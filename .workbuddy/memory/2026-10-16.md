## DSTLauncher 打包分发可行性排查（仅诊断，未改动任何文件）

用户问「打包完是否只有一个 exe、直接给朋友双击就能用」。结论与发现：

### 架构结论
- 单 exe 成立：`//go:embed all:web/dist`（main.go:46）+ `//go:embed options.json`（worldsettings.go:24）
  把前端与选项数据打进二进制；go.mod 零第三方依赖、无 cgo → 不需要 DLL / VC++ 运行库。
  运行时只需 exe 本身，`dst_save/` `logs/` `ugc_mods/` `panel.json` `<workdir>/steamcmd/` 首次启动自建。
- 工作目录取 `os.Getwd()`（main.go:94），不是 exe 所在目录 → 快捷方式「起始位置」写错会让数据落错地方。

### 发现的阻塞问题（本机副本根本编不过）
`go vet ./...` 报两处：
1. `main.go:30: package dst-windows/internal/steamcmd is not in std` —— 本工作副本不存在 `internal/steamcmd/`。
   `git ls-files internal` 里也没有它，`git log --all -- internal/steamcmd*` 无记录 → 该包**从未被提交**。
   根因：`.gitignore` 里有一行裸的 `steamcmd/`（本意是忽略运行期下载的 SteamCMD 目录 `<根>/steamcmd/`），
   但该 glob 匹配任意层级的 steamcmd 目录，把 `internal/steamcmd/` 的源码一并忽略了。
   修法：改成 `/steamcmd/` 锚定根目录，再从开发机把 `internal/steamcmd/` 补回并提交。
2. `main.go:46: pattern all:web/dist: no matching files found` —— `web/dist` 不存在（被 .gitignore 忽略，
   正常），构建前必须先 `cd web && npm run build`。

### 朋友的机器上第一次跑还需要
- DST 专用服务器文件（~2GB）：Steam 库里已装 "Don't Starve Together Dedicated Server" 则自动探测复用，
  否则面板「一键安装」下载 SteamCMD + 服务器文件（需联网）。
- Klei cluster token（在线开服必须；README 提 `.gitignore` 忽略 `个人测试信息.txt` / `*.token`）。
- 面板端口 16800 只绑 127.0.0.1（安全）；开服的 UDP 游戏端口需放行 Windows 防火墙，外网进服还要路由器端口转发。

### 双击体验的坑
- 不会自动打开浏览器（全仓无 rundll32/ShellExecute/start http 调用），需手动访问 http://127.0.0.1:16800。
- 优雅退出只在 Ctrl+C/SIGTERM 路径注册（main.go:246）；直接点黑框的 × 不走 c_save + c_shutdown。
- 目录必须可写（别放 Program Files）；微信/QQ 传输会带上「来自网络」标记，首次运行触发 SmartScreen。

### 交叉编译（Mac 上出 Windows exe）
`cd web && npm run build && GOOS=windows GOARCH=amd64 go build -o dstwin.exe .`

## 追加（用户反驳「防火墙没必要」后的核准）

用户观点：防火墙不该列进交付清单——开服的人自己机器上本来就会处理。认可。

但核准出两个必须保留的事实：

1. **专服不走 Klei 打洞**。Don't Starve Wiki 的 Dedicated Servers 指南原文：专服不使用 Klei 客户端开房那套 punch-through，
   "GSAs must add proper port forwarding for their server to be reachable by game clients"。
   即：客户端「创建游戏」才免端口转发；专服给外网朋友进服必须转发。局域网内玩则只需本机防火墙放行，不碰路由器。
2. **面板不用 Klei 默认端口**。`internal/room/room.go:160-177` 里端口是自动分配的：
   MasterPort=21000；分片 `ServerPort = 11000+i+1`（Master 11001 / Caves 11002）、
   `MasterServerPort = 31000+i+1`、`AuthenticationPort = 41000+i+1`。
   所以网上攻略「转发 UDP 10999」对这套面板**无效**，转发必须以面板里显示的每个房间实际端口为准。

## 交付范围最终确认（用户拍板）

- 交付物 = 只有 `dstwin.exe`；DST 专用服务器文件（~2GB）**由使用者自己下载**（面板「一键安装」或自己在 Steam 装专服工具）。
- 由此，服务器文件、Klei cluster token、防火墙/端口转发三项**全部划归使用者自理**，交付方不预置任何东西。
- 仍卡在交付方一侧的只有编译前提：`internal/steamcmd` 包缺失（见上文 .gitignore 根因）+ `web/dist` 需先构建。

### Token 流程（已核实）
- 用户自己去 Klei 申请（账号页，或游戏内控制台 `TheNet:GenerateClusterToken()`）。
- 面板已有入口，不需要他手动找目录：`Room.Token` 字段（room.go:48）→ 生成时写入 `cluster_token.txt`（generate.go:127）。
- 只有在线开服才需要：`NeedsToken()`（generate.go:193）在 `LANOnly` 或 `Offline` 房间下返回 false，即局域网/离线模式免 token。

### 运行时无外部资源依赖（已全仓核查）
全仓 `os.ReadFile/os.Open` 的目标只有两类：运行时自建文件（panel.json、serverdir.txt、rooms.json、cluster 目录、whitelist.txt、日志、备份、已下载 mod 的 modinfo.lua、服务器安装目录的 version.txt）
+ 编译期已嵌入的资源（`web/dist`、`options.json`）。唯一读外部输入的 `tools/extract-worldsettings` 是独立开发期二进制，不进 exe。
→ 结论：exe 单文件自洽，无伴生文件、无 DLL、无运行库。交付形态确认。

## 重大更正：端口转发不是「必须」（用户实测推翻）

用户实测：他和朋友（外网）已经用过，朋友在游戏里「浏览游戏」就能搜到并进服，没有任何端口转发。

**用户是对的，我上文的判断错了。** 错因：我引用的是 Fandom 那份 Dedicated Servers 指南，页面自己标注
"As of December 5, 2015 ... prior to the official release of caves"，是 caves 进正式版之前的旧版指南，不能套现版本。

核准后的 DST 联网模型（pingaim.com 2026 的协议分析）：
> DST **不使用 Steam Datagram Relay (SDR)**；玩家直连服务器 IP 为主。
> **Klei 提供 NAT 穿透与中继兜底**（direct 失败时回退），所以不转发也能连。

所以两条路径要分开看：
1. **发现/注册**：服务器主动**出站**连 Steam 上报（master_server_port），注册进服务器列表 → 这是「浏览游戏能搜到」的来源，不需要任何入站转发。
2. **游戏数据**：走 server_port，优先直连 UDP；直连不成立时回退 Klei 中继 → **不转发 = 能连（走中继，延迟高一档）；转发 = 直连，延迟更低更稳**。

**最终清单**：删掉「防火墙」；端口转发从「必须」降级为「可选优化（想直连降延迟才做）」。
要转就转该房间面板显示的端口（Master/Caves 两条连接都要，11001/11002 + 31001/31002），不是攻略里的 10999。

## 想做到「② 直连」的操作步骤（已核实面板位置）

- **端口在面板哪看**：房间 → 编辑 → 「分片与端口」（`web/src/components/rooms/PortBoxes.vue`），
  每个分片三个字段：游戏端口 / Steam 主端口 / Steam 认证口，默认 Master 11001·31001·41001、Caves 11002·31002·41002。
  是自动分配的，改动需重启该房间生效（`RoomEditor.vue:230`）。
- **分片协调端口 `masterPort`（默认 21000，`manager.go:47` = cluster.ini [SHARD] master_port）不需要转发**，
  它只是同机两个分片之间的协调通道。
- **四步**：
  1. 确认有公网 IP：路由器 WAN 口 IP 与公网查询结果一致才行；拿到 10.x / 100.64-100.127.x / 172.16-31.x = 运营商 CGNAT，转发无效，需申请公网 IP。
  2. 给开服机固定内网 IP（路由器 DHCP 地址保留），否则重启后规则失效。
  3. 路由器端口转发，协议 **UDP**，每个分片的**游戏端口**必须转（Master + Caves 都转，只转一个会出现「地表能进、下洞穴掉线」）。
  4. Windows 防火墙放行 `dontstarve_dedicated_server_nullrenderer.exe` 入站（专用网络）。
- **验证**：客户端控制台 `c_connect("<公网IP>", 11001)` 能进 = 直连成立；或看路由器转发规则的命中计数。
- **代价**：公网 IP 与开服机暴露在公网，失去 Klei 中继层的遮挡；收益是延迟降一档。属于可选优化，不是必须。

## 决策：放弃「直连/端口转发」方向（用户拍板）

理由（用户提出，认可）：
1. 手动端口转发对普通用户操作成本过高（路由器品牌/型号各异，教程无法穷举）。
2. 前置条件是有公网 IP，而国内家宽 CGNAT 普遍、申请公网 IP 越来越难 —— 这是死结，不是体验问题。
3. **路由器后端实现不一致**（用户补充）：不只是管理界面各不相同，UPnP/IGD 各厂实现参差（默认关闭、IGD v1/v2 SOAP 细节与
   `GetExternalIPAddress` 返回值不一致、映射被租约刷新冲掉）；国内常见「光猫路由模式 + 无线路由器」两层 NAT，
   外层光猫的映射常被运营商锁掉、需超级管理员账号 —— 用户连该配哪一台都判断不了。
   → 结论升级：手动配不了，自动化也靠不住。

推论：这解释了为什么商业游戏普遍走厂商中继/打洞（Steam SDR、Klei relay）——NAT 后面千奇百怪，
唯一能规模化的是「服务器主动出站 + 厂商中继」。本面板复用 Klei 中继不是退而求其次，而是把 NAT 这摊事
交给已有中继基础设施的一方，是正确选择。

评估过的自动化路径：程序内做 UPnP/IGD 映射（SSDP 发现 + SOAP `AddPortMapping`，用户零操作）。
**结论是不做**：它只省掉"手动几步"，救不了"没有公网 IP"（CGNAT 下路由器 WAN 口本身是运营商内网地址，映射出去无人可达）；
且需引第三方库或手写 SSDP/SOAP，会破坏当前 `go.mod` 零第三方依赖的性质。

**替代方案（已确认可行且零网络配置）**：调 tick rate。面板默认 `TickRate = 30`（`room.go:111`），可选 15/30/60（校验在 `room.go:198`）。
协议分析结论：60Hz+80ms 的手感好于 15Hz+20ms —— 提升手感靠拉 tick rate 比降延迟更直接。
代价是 CPU/带宽上升（每分片一个进程、单线程模拟），模组多/人多时要注意机器负载。

→ 交付清单里端口转发彻底删除；"想更顺"改成面板里把 tick 调到 60。
